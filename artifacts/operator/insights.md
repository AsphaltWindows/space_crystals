# Operator Insights

- Legacy tickets live in `qa_human_review/` and `qa_tasks/` at the project root (not inside `artifacts/`). These are from a pre-pipeline era and contain detailed technical context, QA results, and dependency information.
- When grouping tickets thematically, the Syndicate faction has two natural clusters: Agent-centric (commands, gathering, building) and Tunnel/Underground-centric (tunnel interface, HQ production, expansions, enter/exit). These overlap but are distinct enough to split.
- Many tickets have extensive "Technical Context" sections with file paths and line numbers — these are useful for the developer but the designer mainly needs the behavioral/UX descriptions and QA steps.
- `artifacts/qa_router/auto_capabilities.txt` controls routing: grep patterns that match QA instruction lines. All patterns commented out = everything goes to manual_qa. 37 items are stuck in manual_qa pending as of 2026-03-21.
- QA instruction patterns in manual_qa items fall into: stat/component checks, state machine transitions, constraint enforcement, ECS queries (all potentially automatable), and visual/interactive checks (require human). Most items mix both types.
- The pipeline_builder agent does NOT participate in the forum. It's a framework/infrastructure role, not a scheduled pipeline agent. Don't direct forum work to the pipeline_builder — redirect to developer or other pipeline agents instead.
- For visual regression bugs, `git log -p -S "keyword"` on the relevant source files is the fastest way to find what commit introduced the change. The map/world visual systems live in `artifacts/developer/src/game/world/map.rs`.
- The elevation system was added in commit `c5792d1` and affects tile Y positioning via `determine_elevation()` and `ELEVATION_HEIGHT_STEP` (0.1). Any system that uses hardcoded Y values for grid-level rendering (gizmos, overlays) may break when elevation is non-zero.
- When a user asks about "large files" in this project, they likely mean the oversized source files identified in the refactoring review: command_panel.rs (6,357), core.rs (6,054), behaviors.rs (4,481), faction.rs (4,387). These four files contain ~45% of the codebase.
- A refactoring task completing through the pipeline (task_completion + QA pass) does not guarantee meaningful code reduction. Always verify actual file sizes after refactoring claims — check `wc -l` on the files and `git log` for recent commits touching them.
- `cargo check` with default features may pass while `cargo build --no-default-features --features diagnostics` (used by `scripts/build_qa_artifact.sh`) fails. When a user reports "can't compile," always test with the build script too — different feature flags can surface different errors.
- `scripts/add_comment.sh` clears ALL close votes when adding a comment. This is by design but means rapid-fire agent comments in one scheduler cycle wipe each other's votes, causing relaunches. Not a bug — agents should handle being relaunched gracefully.
- Agents killed the scheduler after "consecutive no-work" launches — this was a behavioral bug. The scheduler is user-managed only. If agents misbehave with the scheduler, the fix goes through the pipeline_builder (which does NOT read the forum — communicate directly with user).
- For multi-round forum discussions that evolve significantly, the original close votes become stale. Use `add_comment.sh` to post a pivot comment — it clears votes and forces re-engagement. Consider whether a new topic is cleaner if the original title no longer reflects the discussion.
- When a forum discussion produces an architecture_request, new user directions added to the forum after the request was sent may not be seen by the task_splitter in time. Time-sensitive scope changes may need direct intervention beyond forum comments.
